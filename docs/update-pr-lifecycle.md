# 更新 PR 的处理流程

工作流负责确定性的更新、生成、测试和状态记录，不调用 Codex 或其他模型。维护者仍决定是否采用、合并或关闭更新。

## 触发与推进

1. 每周定时、main 推送或手动执行 `Resource updates`，检查固定上游并在隔离候选中完成来源构建和 marketplace 生成。
2. 通过的候选创建或刷新同一更新组的 PR；单组失败不丢弃其他组的候选。来源缺少映射、原文记录或存在本地适配时，报告具体原因，等待维护者处理，不自动猜测或修改适配。
3. PR 写入成功后显式 dispatch main 上的 `Validate PR head`。这条路径不依赖机器人写入引发的普通 PR workflow 是否需要批准；只给 PR 发布 job 增加 `actions: write`，该 job 没有私有来源密钥。
4. 普通人工或 Dependabot PR 的 `Validate tooling` 完成后也会触发协调验证。协调器从 GitHub API 重新读取 run 和 PR，不信任传入事件中的任意提交或分支；只检查本仓库、main 为目标且未关闭的准确 head。
5. 普通代码测试和私有来源验证在分离的 job 中运行，分别回写两项必需状态。任何失败保留失败，取消或跳过不能算通过；PR head 已移动时忽略旧结果。可从 Actions Summary 查看 `ready-for-review`、`needs-attention` 或 `superseded`。
6. 两项检查通过后由维护者审阅并合并。main 上再次验证并发布基线，同时触发下一次候选刷新，让其他未完成的更新跟上 main。

PR 仍保持原有 draft/ready 状态，机器人不自动批准、合并或关闭 PR，也不自动安装资源。合并后分支删除沿用仓库现有设置或由维护者操作；不会为了清空列表删除人工工作。通过 CI 与采用更新是两件事。

## 分支刷新

普通的 GitHub “Update branch” 会增加 main 合并提交。机器人现在会用 Git 对象证明这些提交只是无额外改动的自动合并，证明通过即可基于最新 main 重新准备候选，生成最新 marketplace，并使用准确 lease 刷新原 PR。

真正的人工代码改动、人工冲突解决、PR 标题/正文修改或来源身份不符仍停止自动接管。需要维护者继续处理这些 PR，或明确整理后重新交回自动化。机器人不会把所有非机器人提交当作可以覆盖的内容。

## 失败与重试

- 候选构建失败：在更新任务 Summary 和 artifact 中保留资源组及原因，其余可用组继续发布。
- 推送或 PR 写入失败：报告 `partial`，保留已完成的操作及不确定状态，不假装回滚。
- 验证调度失败：已写入的 PR 保持原样；下次相同候选可重试验证，不重新创建 PR 或重复推送。
- 两项准确 head 的状态已成功：重复同步不再 dispatch 验证；失败或缺失时允许重试。
- PR 被人工关闭且上游目标未变：尊重原有拒绝决定，不重新创建同一候选。

调度与固定来源访问边界见 [私有来源 CI](private-source-ci.md)；生成规则见 [市场生成](marketplace-generation.md)。
