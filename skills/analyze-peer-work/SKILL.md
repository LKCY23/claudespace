# 需求驱动的参考工作分析与借鉴

围绕用户自己的目标理解参考工作，判断哪些思路和实现适用，并将分析转化为可读、可追溯、能够服务后续工作的成果。参考对象可以是论文、项目、框架、技术方案或其他团队的实现；不预设被推荐的工作一定优秀，也不预设必须采用它。

## 必须遵守的分析原则

这些原则约束相关判断的质量，不要求在每次回答中逐条展示，也不规定章节、表格或文件。

1. **以实际需求为基准。** 从用户指令、项目材料和已有讨论识别目的与约束，区分当前必需条件、比较维度、长期方向和待验证假设。发现更合适的问题定义时，说明修订理由；不能把推测或参考工作的特点悄悄变成用户的既定需求。
2. **先准确理解对方的问题设定。** 在其目标、假设、约束和责任边界下解释设计选择，再评价与我们的适配程度。不同范围、明确非目标或尚未检查的能力，不能直接写成实现缺陷或能力不存在。
3. **使结论强度匹配证据。** 区分作者主张、设计声明、源码机制、已观察的运行或实验结果，以及我们的推断。关键事实应有可核查来源；版本、配置和验证范围影响判断时明确记录。代码存在不等于运行有效；单个案例不证明普遍适用；缺少证据不等于反证。已有笔记中的关键事实若未复核，应保留这一限制。
4. **保持概念、分类和比较口径一致。** 分清流程阶段、职责模块、接口、替换单元、组合机制、部署方式等维度。比较多个工作时使用共同需求与可比条件；无法直接比较的部分说明原因。可以提出自己的分析视角，但要与对方原有分类区分，不能借重新命名夸大其能力或我们方案的差异。
5. **让评价与借鉴回应具体问题。** 重要评价应说明它如何影响用户的需求。提出采用、适配或替换建议时，交代可借鉴的内容、适用前提、必要调整、主要成本及有效性如何检查。可借鉴的是问题理解、设计思路、具体实现或验证方法，不一定是代码。证据不足时提出有针对性的验证或保留判断，不强行推荐或排名。
6. **整理时保留语义和成熟度。** 重组材料不得丢失会改变结论的条件、反例、来源或不确定性。明确区分已知事实、解释、候选建议和已确认决定；图文使用一致的术语与边界。只整理既有材料的任务，不借成稿之机新增未经支持的设计结论。

## 可调整的工作方式

以下三个方面组成推荐工作路径，可以交错、回访、合并，或从已有材料中途接入。它们不是必须逐步确认的审批阶段，也不是输出模板。根据问题的重要性和证据缺口分配工作量。

### 明确需求与判断基准

先利用上下文和已有项目材料，确认这次分析要帮助理解或决定什么。需求已有明确表述时，简要提取即可；缺失信息会实质改变方向时，集中询问关键问题，并继续不依赖该答案的工作。不要重复索取已经给出的目标。

把宽泛要求转成能够追问和检查的问题。例如，“需要可组合性”可以细化为：组合什么对象、哪些状态需要共享、替换时允许改动什么、希望开展什么实验。使用哪些维度取决于任务，不默认采用通用评分表或人为权重。

需要澄清的通常是：使用场景、当前困难、待决策事项、约束、关注的长期边界，以及分析结束后希望获得的判断。它们可以用几句话记录，不要求独立的需求文件。

### 理解机制并评价适用性

先建立足够的整体认识，再沿优先问题深入。一个有用的追问方向是：

> 面临的问题 → 采用的抽象与设计 → 实现机制 → 带来的能力 → 成立条件与限制

这条链用于检查解释是否完整，不要求每个发现填满五个字段。按问题选择原始论文、官方文档、源码、测试、运行记录或实验结果。采用最直接的证据；关键来源矛盾时核对版本和上下文，保留仍未解决的分歧。

对于系统与实现问题，可以选择代表性案例，追踪输入、调用、数据或状态变化、输出和控制边界，理解接口实际连接了什么。只有疑问确实涉及失败处理、恢复或资源控制时，才继续追这些路径；不默认穷尽仓库或运行完整实验。文档用途的补查应集中在会改变主要结论的缺口。

把发现放回需求中，解释适用范围与差距。必要时用“我们的问题／标准—对方机制与证据—适用条件—对我们的建议”帮助比较；也可以采用连贯叙述或其他更适合的表示。不要机械要求所有工作都能给出一个总分或唯一赢家。

当证据足以支持当前判断，或进一步判断明确依赖新的信息或实验时，整理已有结论和限制。实际获得验证结果后，修订相关建议及理由；仅建议了实验时，不写成已经验证。

### 重组为可读成果

围绕读者、用途和需要支持的判断组织内容。探索过程的时间顺序可以保留在记录中；成稿通常按理解依赖展开，让读者知道每部分为何出现、怎样支撑后续判断。

一种可选叙述主线是：研究动机与需求 → 工作的核心思路 → 关键机制与边界 → 适用性和借鉴 → 对后续工作的影响。已有读者背景、多个独立问题或纯材料整理任务，可以采用不同顺序、合并部分或省略已经明确的内容。

- 正文保留理解主要判断所必需的信息。消息清单、源码导航和详细证据需要保留时，可使用附录或链接。
- 图表先确定表达目的，再选择内容；流程图说明顺序、架构图说明关系与边界、对照表帮助比较、伪代码说明执行配合。按需要选用，不规定图片数量、固定图型或必须包含代码。
- 图、文字和代码各自承担有用的解释任务，避免把大段正文搬进图中。简洁不能以丢失关键条件或逻辑连接为代价。
- 已有提纲、文档约定和用户手动调整优先保留，确需重组时说明依据。组织建议不能替代用户指定的格式。

## 产出与完成判断

交付与用户请求的深度一致：初步判断可以很短；深入调研应提供足够的机制与证据；已有分析成稿主要完成重组和必要补查。使用用户的语言和读者能够理解的表达。

在本次范围内，成果应使读者看清：分析为何开展、参考工作的相关机制、判断依据及限制，以及这些认识如何帮助当前工作。任务涉及借鉴时，再明确采用条件、调整或验证事项；尚未成熟的设计可以作为讨论问题，不强行补全实施方案。

检查重要问题是否已回答或注明未决原因，关键判断是否可追溯，读者是否无需原始聊天也能理解。这里约定的是信息充分性，不要求固定标题、顺序、篇幅、表格或文件集合。

只要求讨论时在对话中交付；要求持久化时遵循指定位置和现有文档体系，优先更新合适的材料。调研与借鉴建议本身不扩大任务到代码修改、部署、发布或昂贵实验。
